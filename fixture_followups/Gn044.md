## OCCT source pointer + prose

Branch (prose-laundered): the convert-to-Bezier path for 2D curves
checks the input degree; when the curve is already degree-1, an early
return skips the degree-elevation step. Downstream consumers expect a
Bezier basis even from the degree-1 path; the skip leaves the curve in
its original (non-Bezier) form, breaking the post-condition.

## Attempts

### Attempt 1 (wave-N) — REFUTED

- **Approach**: B-spline curve with three control points declared at
  degree 1, then a knot multiplicity vector `(1, 1, 1, 1)` summing to
  4.
- **Refutation**: Knot multiplicity sum is wrong — Part-21 B-spline
  requires `sum(knot_multiplicities) == n_control_points + degree + 1`.
  For 3 control points at degree 1 that is `3 + 1 + 1 = 5`, not 4.
  Fixture fails parser-level B-spline validation before
  ConvertCurve2dToBezier is ever invoked.

## Why it's hard

The defect lives in a code path that requires a *valid* degree-1
B-spline as input. Reaching it means satisfying the parser's knot-sum
invariant first, then having degree-1 geometry that's interesting
enough that the downstream consumer would actually call
ConvertCurve2dToBezier on it.
