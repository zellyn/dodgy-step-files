## OCCT source pointer + prose

Branch (prose-laundered): ShapeAnalysis_Curve::IsPlanar builds a
plane-of-best-fit from the curve's pole positions. With a NaN
component anywhere in a pole, the resulting plane normal carries the
NaN forward without an explicit `isnan` guard, so downstream
planarity comparisons against `Precision::Confusion()` always return
false — meaning a curve that *would* be planar after sanitization is
classified as non-planar, and a polluted curve that should be flagged
as malformed silently slips through with the same "non-planar"
verdict.

- **Refutation**: Adversarial reviewer accepted that the NaN pole

  The parser rejects the file before any IsPlanar pass runs.

## Why it's hard

NaN handling defects are interesting because they affect what *would*
happen if the parser tolerated the NaN. But STEP parsers (including
OCCT's) often reject `NaN` literals at the lexer level, before any
healer sees the data. Constructing a fixture where NaN reaches IsPlanar
requires a parser that accepts `NaN` as a REAL token — not guaranteed.

## Next directions

- Move all entity declarations *inside* the DATA section before
  `ENDSEC`. The current Gn090 has `#200` declared after `ENDSEC` —
  fix by reordering.
- Verify that OCCT's STEP reader actually parses `NaN` as a REAL
  literal (it may not — check). If not, this defect is only
  reachable through a kernel-test-pair where the NaN is injected
  post-parse via the runtime API.
- Alternative: use a very-small denormal that survives parse but
  trips the planarity tolerance — closer to "real-world malformed"
  than a synthetic NaN.
