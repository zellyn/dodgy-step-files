N049 — Reading a structurally valid STEP file produces an invalid `TopoDS_Shape`

Sources

  • OCCT MANTIS#0024055
  • bug-reporter language: "reading a STEP file produces invalid shape", "BRepCheck reports errors after STEP import", "imported shape fails BRepCheck_Analyzer". (OCCT MANTIS tracker 502 as of 2026-05-02)

Sender

Producers whose `EDGE_CURVE` end-vertex coordinates do not lie exactly on the underlying curve at the receiver's tolerance, or whose face boundary loops are not perfectly closed.

Description

A STEP file imports without diagnostic, but `BRepCheck_Analyzer` on the resulting shape returns `BRepCheck_InvalidPointOnCurve` / `BRepCheck_NotClosed` / `BRepCheck_InvalidWire`. The defect is at the boundary between the producer's tolerance and the receiver's: the file is structurally legal, the geometry is "almost" valid, and the reader silently accepts but downstream operations (Boolean, mesh, sewn-shell promotion) fail with cryptic errors. Distinct from M160 (silent-empty); here a shape is produced, but it is not valid.

Reproducer recipe

`EDGE_CURVE` whose end-vertex `CARTESIAN_POINT` is at distance `2e-6` from the curve at the curve's parameter; receiver's edge tolerance is `1e-7`. Reader imports; `BRepCheck` flags.

Expected kernel behavior

heal-and-accept; auto-bump edge tolerance during import to the maximum of the producer's claimed tolerance and the measured point-on-curve deviation; emit `W_TOLERANCE_BUMPED`. Downstream operations should never see an invalid shape.

Notes

**See also**: N015, N028, Twi099. Synonyms: "reading STEP file produces invalid shape", "BRepCheck flags imported shape", "STEP import yields shape that fails Analyzer", "tolerance mismatch between producer and receiver".
