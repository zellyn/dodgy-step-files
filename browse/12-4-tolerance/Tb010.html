Tb010 — Self-intersection that vanishes when round-tripped through float32

§12.4 (sub-class: rounding-induced topology change)

P1 — silent data loss

Description

Variant of Tb009 where the rounding is done by the format-converter step (e.g. STEP → STL → STEP through a tool that uses `float` not `double`). Coordinates `(0, 0, 0)`, `(1.0000003, 0, 0)`, `(2.0000007, 0, 0)`, `(0.9999997, 0.0000003, 0)` form a near-degenerate quad whose diagonals cross. After float32 round-trip the coordinates collapse to `(0, 0, 0)`, `(1, 0, 0)`, `(2, 0, 0)`, `(1, 0, 0)` — the diagonals no longer cross because the duplicate point makes one edge zero-length. The "fix" was unintentional precision loss.

Reproducer recipe

Quad face with above coordinates exactly; wrap in PRODUCT chain. The fixture itself uses double precision so the self-intersection is real; the time bomb is documented in the comment as "input was generated by a float32-precision producer".

Expected kernel behavior

Warn and accept: results normalize to be invariant under coordinate precision changes within the operating range; if not invariant, the kernel emits a warning diagnostic flagging the precision sensitivity.

Notes

Synonyms: "self-intersection lost when round-tripped through float32", "float32 round-trip removes crossing", "single-precision conversion masks self-intersection", "intersection visible in double precision only".
