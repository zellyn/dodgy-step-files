Ls033 — Whitespace handling: tab/CR/LF/FF as token separators or ignored chars

§12.1c whitespace

P1 — silent data loss

syntax

View raw fixture (.stp) step-examples/12-1c-syntax/Ls033.stp

Sources

  • T031, T032, T037, N030, N031

Description

ISO 10303-21 §5.2 says LF, CR, TAB, FF are ignored characters; §5.6 says only SPACE, comments, and print directives separate tokens. Strict reading: `#1\t=\tCARTESIAN_POINT(..)` after tab-removal becomes `#1=CARTESIAN_POINT(..)`, but `#1<TAB>2` would become `#12`. Real-world parsers tolerate any ASCII whitespace as a separator. Defects: split keyword `FILE _SCHEMA`, internal whitespace inside `#NNN` references, files with `\r`-only line endings, `\f` between attributes, long-line wrapping inside an instance.

Reproducer recipe

`FILE _SCHEMA(('AUTOMOTIVE_DESIGN'));`, `# 12 = IFCPERSON(..);`, file with CR-only line endings, `#1=IFCPOINT(\F\(0.,0.,0.));`

Expected kernel behavior

Treat any of `\t \f\r\n` as whitespace separator (matches user expectation); preserve line/column counting across line-ending conventions; warn on TAB inside an identifier; accept print-control directives `\F\` and `\N\` as zero-width separators where token separator is allowed; reject embedded whitespace inside `#N` (between `#` and digits).

Notes

**See also**: Le028. Synonyms: "tab as STEP token separator", "FF as token separator", "tab between # and =", "ignored char inside STEP token", "whitespace handling in STEP scanner".

  • matches(rb'#\s+\d')
