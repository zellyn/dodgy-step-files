Wr029 — `FILE_DESCRIPTION` strings containing newlines or unescaped control characters

§12.13 writer-pathology (sub-class: header / vendor metadata)

silent-loss writer

View raw fixture (.stp) step-examples/12-13-writer-pathology/Wr029.stp

Sources

  • OCCT forum "header description has line break"
  • bug-reporter language: "string in STEP wraps mid-line"

Sender

Writers that paste user-entered description text into `FILE_DESCRIPTION` without escaping line breaks

Description

A `FILE_DESCRIPTION(('line one\nline two'),'2;1')` where the literal `\n` is an embedded newline (not the two-character escape — the actual 0x0A byte) terminates the string for crude line-based parsers. Spec violation per ISO 10303-21 §6.4 (control characters in string literals). Bug-reporter language: "STEP file string has line break", "FILE_DESCRIPTION corrupt".

Reproducer recipe

literal `FILE_DESCRIPTION(('first line` (newline) `second line'),'2;1')`.

Expected kernel behavior

reject as malformed per spec; do not silently splice the broken string back together because the splice point is undefined.

Notes

Le017 covers from read side; Wr029 attributes to writer. **OCC behavior**: silently accepts the broken-string file (no diagnostic, empty result); kernel mishandling — not what kernels should do.

Expected validation

occt=empty/empty gmsh=empty ifc=schema_n/a

Byte assertions

  • matches(rb"FILE_DESCRIPTION\(\('[^']*\n[^']*'")
  • matches(rb"FILE_DESCRIPTION\(\(\s*'[^']*\n")
