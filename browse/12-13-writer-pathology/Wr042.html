Wr042 — Inconsistent end-of-record terminator: `;\n` and `;\r\n` mixed in same file

§12.13 writer-pathology (sub-class: whitespace/line-ending)

P3 — cosmetic / metadata-only

crash writer

View raw fixture (.stp) step-examples/12-13-writer-pathology/Wr042.stp

Sources

  • bug-reporter language: "STEP file mixed newlines per record", "writer outputs CRLF then LF inconsistently"

Sender

Multi-pass writers where one pass appends records via a buffered text stream (LF) and a separate pass appends records via a Windows-line-ending logger (CRLF), interleaved within the same DATA section

Description

Records inside a single DATA section terminate with mixed `;\n` and `;\r\n` line endings. The spec is silent on line-ending conformance — whitespace is whitespace — but tools that line-count for diagnostics report inconsistent line numbers, content-hash caches see the file as different on each export, and editors display the file as binary. Cousin of Wr002 (HEADER vs DATA section uses different line ending) but at the per-record granularity. Bug-reporter language: "STEP file mixed newlines per record", "diff of exports is full of line-ending changes".

Reproducer recipe

a DATA section where alternate records terminate with `;\n` and `;\r\n` — for example `#1=APPLICATION_CONTEXT('automotive_design');\n` followed by `#2=PRODUCT_CONTEXT('part',#1,'mechanical');\r\n`.

Expected kernel behavior

parsers must accept (whitespace tolerance); writers should be deterministic per-file. A normaliser is the simplest fix.

Notes

**See also**: Wr002, Le028.

Expected validation

occt=empty/empty gmsh=empty ifc=process_signal

Byte assertions

  • contains(b';\r\n') and contains(b';\n')
  • count(b'\r\n') >= 1 and count(b'\n') >= 5
