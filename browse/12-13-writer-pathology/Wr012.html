Wr012 — Random `#N` numbering with no monotonic structure

§12.13 writer-pathology (sub-class: instance numbering)

P3 — cosmetic / metadata-only

writer

View raw fixture (.stp) step-examples/12-13-writer-pathology/Wr012.stp

Sources

  • OCCT forum "STEP file has random instance numbers"
  • bug-reporter language: "instance numbers jump around"

Sender

Writers that allocate instance numbers from a hashed pool keyed on entity-identity rather than emit-order; observed in some Java-based exporters

Description

Instance numbers in the DATA section follow no monotonic pattern: `#1`, then `#1000`, then `#5`, then `#1003`, then `#7`. The spec does not mandate monotonic numbering, so the file is well-formed; but human reviewers, line-based diff tools, and forward-reference-detecting linters all stumble. Bug-reporter language: "STEP instance numbers are random", "file numbering jumps", "can't follow refs visually".

Reproducer recipe

a Part-21 file in which the order of `#NNN` in the DATA section is `#1, #1000, #5, #1003, #7, #1006`.

Expected kernel behavior

Heal and accept: parse normally; numbering is content-addressable, not order-bearing; a re-emit policy may normalize / renumber sequentially.

Notes

Discoverability is the main cost; correctness is unaffected.

Expected validation

occt=empty/empty gmsh=empty ifc=schema_n/a

Byte assertions

  • matches(rb'(?s)#1=.*#1000=.*#5=')
  • count(b'#') >= 6
