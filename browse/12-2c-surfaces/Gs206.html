Gs206 — VECTOR with negative magnitude violates ISO 10303-42 `vector` WR1; every oracle accepts it silently

  • first fixture of the WHERE-rule-mining vein (the AP242 MIM schema declares 1154 WHERE rules).

Description

The seam-edge `LINE` takes its direction from `VECTOR('neg_mag',#dir,-L)` — a valid `DIRECTION` but a strictly **negative** magnitude, which violates `vector` WR1 (`magnitude >= 0.0`). OCCT (and gmsh) accept the file and build the solid — `shape(1)`, non-null — with no diagnostic; `part21_strict` accepts (a negative real is valid Part-21 syntax); the non-kernel structural linter is silent. Every oracle here tolerates the WHERE-rule violation, which is exactly the class of formal constraints OCCT does not enforce.

Reproducer recipe

any reachable `VECTOR(name, #direction, magnitude)` whose `magnitude` literal is negative — here the seam `LINE` of a clean truncated-cone `MANIFOLD_SOLID_BREP`, so the negative-magnitude vector is on the transfer path.

Expected kernel behavior

reject a negative `vector` magnitude at parse (per WR1), or normalise it (flip the sign into the direction); never silently propagate a negative magnitude into geometry.

Notes

RUNTIME-VERIFIED (2026-08-14, OCP/OCCT 7.8.1): `occt=shape(1)/shape(1)`, part21 accepts, structural ok — every oracle silently tolerates the WR1 violation. Distinct from Gs036 (zero-magnitude / negative-radius): magnitude 0 is **permitted** by WR1 (`>= 0`), so only a strictly-negative magnitude violates it. gmsh count (shape(7)) is CI-Linux-authoritative if it diverges. Synonyms: "negative VECTOR magnitude", "vector magnitude below zero", "ISO 10303-42 vector WR1 violation", "negative-magnitude direction vector". Provenance tier: bytes-sufficient.
