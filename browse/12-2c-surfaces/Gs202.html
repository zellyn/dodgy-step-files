This is the SAME function Gs029 (periodic wrap), Gs201 (bounded-curve clamp), and Twi086 (`w1==w2`) exercise — this fixture targets its curve-reversal fallback, reached only when the curve is `Geom_BSplineCurve`, genuinely NOT closed (`StartPoint().Distance(EndPoint())` well above tolerance — unlike Gs203/the tolerance-closed subvariant), and the vertex-projected parameters still come out reversed (`w1 > w2`).

Description

A single `ADVANCED_FACE` on a `PLANE` has one boundary edge whose 3D curve is a clamped, non-periodic, non-closed degree-3 `B_SPLINE_CURVE_WITH_KNOTS` (4 poles, single span, control points `(0,0,0)→(2,3,0)→(4,3,0)→(6,0,0)`, an open curved arc). The `EDGE_CURVE`'s own `VERTEX_POINT`s are SWAPPED relative to the curve's own parametrization: `edge_start` sits at the curve's TRUE end pole `(6,0,0)` and `edge_end` sits at the curve's TRUE start pole `(0,0,0)`. Vertex-to-curve projection is unambiguous (exact pole matches, 3D distance between the two poles is 6.0 — far beyond any tolerance, so this is NOT the tolerance-closed case), yielding `w1=1.0` (the curve's own last parameter) and `w2=0.0` (the curve's own first parameter) — a clean, confident, fully reversed-order result.

Reproducer recipe

`B_SPLINE_CURVE_WITH_KNOTS('name',3,(p0,p1,p2,p3),.UNSPECIFIED.,.F.,.F.,(4,4),(0.0,1.0),.UNSPECIFIED.)` as `EDGE_CURVE.edge_geometry`; `VERTEX_POINT`s at `p3`'s coordinates (edge_start) and `p0`'s coordinates (edge_end) — i.e. the edge's start/end vertices literally at the curve's own last/first control points, in that swapped order.

Expected kernel behavior

the edge-parameter-range repair stage must detect `w1 > w2` on this ordinary (non-periodic, non-tolerance-closed) B-spline curve and repair it by PHYSICALLY REVERSING the curve (flipping the pole/knot sequence) and remapping both parameters to their reversed equivalents — producing a curve whose own `[FirstParameter, LastParameter]` range is increasing again and whose endpoint values at the new range bounds match the edge's actual vertex coordinates, rather than either leaving the range inverted (undefined edge geometry) or silently swapping only the numeric values without re-orienting the underlying curve (which would misalign every intermediate sample point along the arc, not just the endpoints).

Notes

Live-verified directly against the fixture's own bytes (default read — this parameter-range repair runs unconditionally as part of ordinary edge translation): the resulting edge's 3D curve reports parameter range `(0.0, 1.0)` (increasing, confirming the reversal fix applied, not a raw `(1.0, 0.0)` inverted range); evaluating the (now-reversed) curve at its own new `w1=0.0` gives `(6.0, 0.0, 0.0)` — matching `edge_start`'s vertex coordinates exactly — and at `w2=1.0` gives `(0.0, 0.0, 0.0)` — matching `edge_end`'s vertex coordinates exactly — confirming the curve's pole sequence was genuinely reversed (not just the parameter labels), so every point along the arc (not only its endpoints) is now correctly oriented; the resulting face closes as a valid quadrilateral (one curved side), area `15.0`, `shape_null=False`. Fills `stp-edge-curve-param-range`'s previously-missing "reversed order on an ordinary curve → curve reversed and parameters swapped" subvariant (1 of 3 missing; see also Gs201, and the deferred tolerance-closed subvariant in `BACKLOG.md`). Synonyms: "EDGE_CURVE vertices swapped relative to B-spline parametrization", "edge-parameter-range repair's curve-reversal fallback", "curve physically reversed and parameters remapped as edge repair", "w1 greater than w2 ordinary non-periodic non-closed curve", "vertex-to-curve-direction mismatch physically reversed not just swapped".
