Description

`MANIFOLD_SOLID_BREP` over a two-face `CLOSED_SHELL`. The first face is a `CONICAL_SURFACE` (reference radius 5 at z=0, 45° semi-angle, so the apex is exactly (0,0,-5)); its `FACE_OUTER_BOUND` is the z=0 rim circle and its inner `FACE_BOUND` is a `VERTEX_LOOP` at the apex vertex — the Part-42 encoding for a boundary that collapses to a single point. The second face is the planar disk closing the rim. Nothing here is malformed: this is a correct, ordinary cone, and the fixture's job is to assert that a healing pass leaves the degenerate apex edge alone.

Reproducer recipe

`CONICAL_SURFACE` `ADVANCED_FACE` with a `FACE_OUTER_BOUND` on the base-circle `EDGE_CURVE` and a second `FACE_BOUND` whose loop is a `VERTEX_LOOP` referencing a `VERTEX_POINT` placed exactly at the cone's apex; close the shell with a planar disk on the same rim edge; sew at tolerance 1e-2.

Expected kernel behavior

the `VERTEX_LOOP` becomes a wire holding one zero-length edge, with the same vertex at both ends and NO 3D curve, formally flagged degenerate; the sewing pass must recognise the flag and copy the edge through unchanged — no small-edge measurement (there is no curve to measure), no removal, no vertex gluing, no boundary-candidate registration — and report it as a degenerate shape rather than as a repaired or deleted one.

Notes

Why we believe this test is valid — live-verified against this fixture's own bytes (this worktree's `validation/.venv`, OCP/OCCT 7.8.1). Default read → shape_null=False, 2 faces; the apex edge comes back with identical start/end vertex at (0,0,-5), `BRep_Tool::Degenerated` True and `BRep_Tool::Curve` NULL — there is literally nothing to measure a length from, so a pass that reached the small-edge branch could not evaluate it. `BRepBuilderAPI_Sewing(1e-2)`.Perform() → `NbDegeneratedShapes()==1`, `NbFreeEdges()==0`, `NbContigousEdges()==0`, `NbDeletedFaces()==0`, and the apex edge is present in the result unchanged: same two coincident vertices, still flagged degenerate. Nothing was repaired, removed or collapsed — which is the whole claim. Perturbation, same generator: replace the apex bound with a GENUINE circle of radius 0.05 just below the apex (small, but not formally degenerate) → `NbDegeneratedShapes()` 1 → 0 and `NbFreeEdges()` 0 → 1, i.e. the edge is now registered as a free boundary and enters ordinary processing. The degeneracy flag is therefore load-bearing for the observed outcome, not incidental. Also recorded, verified and mildly surprising: OCCT normalises BOTH STEP encodings of a collapsed boundary — this fixture's `VERTEX_LOOP` and Gs189's radius-0.0 `CIRCLE` — to the same in-memory shape, a degenerate edge whose 3D curve handle is null; the two fixtures differ as INPUT patterns (what a consumer must survive) while converging on the same kernel branch. The read also completes the cone face's boundary with a computed seam line from the apex to the rim, so the loaded shape has 3 unique edges (tier-3 `n_edges_total`=5 counts loop occurrences). Synonyms: "cone apex vertex loop degenerate edge STEP", "must not remove degenerate edge sewing", "zero-length edge legitimate not defect", "VERTEX_LOOP face bound apex", "degenerate edge no 3D curve pass through".
