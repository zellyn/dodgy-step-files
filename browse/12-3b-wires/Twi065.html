Twi065 — Wire edge-curves analysis: 3D/2D consistency in one report (EDGE_LOOP with reversed pcurve direction, vertex/3D LINE start mismatch, junction gap, and pcurve/3D length parameter mismatch)

Sources

  • OCCT `ShapeAnalysis_Wire::CheckEdgeCurves` (`ShapeAnalysis_Wire.hxx:208`)

Description

For a wire (EDGE_LOOP) whose edges variously fail CheckCurve3dWithPCurve, CheckVerticesWithPCurve, CheckVerticesWithCurve3d, CheckSeam, CheckGap3d, CheckGap2d, CheckSameParameter — the analyzer must run all these checks and surface every status flag, even when earlier checks already flagged the wire as defective. Typical fixture: a four-edge EDGE_LOOP combining distinct defects (edge1 with pcurve direction reversed relative to 3D LINE, edge2 with 3D LINE start point disagreeing with VERTEX_POINT, edge3 starting offset from previous endpoint leaving a junction gap, edge4 with pcurve length not matching 3D length — same-parameter violation).

Reproducer recipe

A four-edge EDGE_LOOP where each EDGE_CURVE fails a different check (pcurve direction reversed, vertex vs 3D-line start mismatch, 3D junction gap, pcurve/3D length mismatch).

Expected kernel behavior

Heal and accept: normalize a per-edge, per-check status grid; no early termination.

Notes

Sub-pipeline of Twi064. Synonyms: "wire edge curves analysis combined report", "per-edge per-check status grid for wire", "edge consistency check across spatial and parametric", "exhaustive edge curve diagnostics". 2026-07-12 regen (exchange VERDICT_AUDIT.md "Fixture-citation hygiene" finding): this entry's edge4 claim (pcurve parameter length 5.0 vs 3D arc length 10.0) was byte-verified to have ZERO `PCURVE` entities anywhere in the shipped file — the old construction only set the 3D `LINE`'s STEP `VECTOR` magnitude to 5.0 instead of 10.0, which has NO effect on OCCT's evaluation (`Geom_Line` is always unit-speed/arc-length parametrized regardless of the stored `VECTOR` magnitude), so the claimed defect was never actually encoded. Fixed per the Gp022 pattern (independently verified as a genuine SameParameter-lie construction): edge4 now carries a REAL `PCURVE` — a degree-1 `B_SPLINE_CURVE_WITH_KNOTS` on the same `PLANE` (control points UV(0,10)→UV(0,0), knot values `(0.0,5.0)`) tracing the identical spatial path as the correct 10-unit 3D `LINE`, but with a parameter-domain width of 5.0 — a genuine 2:1 pcurve/3D-arc-length mismatch under `EDGE_CURVE`'s `same_sense=.T.` assertion. Edges 1-3 are unchanged (their claims — reversed wire-traversal orientation via `ORIENTED_EDGE` `.F.`, vertex/3D-line start mismatch, junction gap — do not require a `PCURVE` entity and were already genuine). Live-reverified 2026-07-12: `occt_heal_on`/`occt_heal_off` both `shape(1)`, `gmsh_autofix_on`/`off` both `shape(9)`, `ifcopenshell=schema_n/a` — IDENTICAL to the previously-recorded Expected line below (no NEEDS-ORACLE-REFRESH; confirmed no drift). `tier3_geometric.geometric_report` (live): shape_null=False, n_faces_total=1, n_edges_total=4, n_vertices_total=8, face[0].surface_type="plane" — all three Tier-3 assertions below still hold (n_vertices_total lands exactly at the `>=8` boundary).
