Lh048 — STEP reader cannot consume a non-seekable stream (in-memory / pipe / network)

§12.1b header structure & instance numbering (sub-class: pipeline / I/O API)

P1 — silent data loss

syntax

Sources

  • OCCT MANTIS#0027342
  • bug-reporter language: "STEP support C++ streams for import", "reader requires a filesystem path", "no way to import from in-memory buffer". (OCCT MANTIS tracker 502 as of 2026-05-02)

Sender

Server-side / sandboxed pipelines that hand the kernel a `std::istream` or memory buffer rather than a filesystem path.

Description

The STEP reader's public API takes a filesystem path and internally `fopen`s it. A consumer that has the STEP content in memory (downloaded from object storage, unzipped from a `.stpz` wrapper, or read from a pipe) is forced to spill it to a temporary file first; which fails on read-only / chrooted hosts and adds I/O cost. The bug class is "API expects path; offers no stream entry point", and the on-disk file content is well-formed; the defect is in the reader's I/O contract.

Reproducer recipe

well-formed minimal STEP file (10-line cube). The catalog entry documents that consumers must spill to disk because the reader has no `Read(std::istream&)` overload.

Expected kernel behavior

heal-and-accept; provide an `istream`-based read entry point; never require a seekable filesystem path. Document that producers may call the stream-based API directly.

Notes

**See also**: Pf022. Synonyms: "STEP reader requires file path", "no in-memory STEP import", "cannot read STEP from std::istream", "API needs filesystem path".
