Pf037 — Two-pass loader: dangling forward-ref subgraph silently truncated (BRL-CAD step-g)

Sources

  • BRL-CAD `src/conv/step/STEPWrapper.cpp` `WARNING: <name> is not valid` diagnostic
  • `entity_status[id] = STEP_LOAD_ERROR` set during pass-2 but never consulted by shell/solid consumers
  • bug-reporter language: "step-g imports a 50 MB STEP file and the resulting .g lacks a subassembly with no obvious error", "WARNING is not valid scrolled past in the import log", "step-g entity_status STEP_LOAD_ERROR not propagated".

Sender

Large-assembly STEP files where one entity record is structurally well-formed (so pass-1 instantiates a stub object) but references a downstream entity that itself failed to instantiate (e.g. a malformed complex-entity record). Common in fuzzed inputs and in CAD-system exports that emit forward references the writer never validated.

Description

BRL-CAD step-g uses a two-pass loader: pass-1 walks the DATA section and instantiates one C++ object per STEP entity, registering each via id; pass-2 walks the list again, calling `Load()` on each object, which dereferences forward references through the id→object map. When a referenced id was never created in pass-1 (or has `entity_status = STEP_LOAD_ERROR`), pass-2 marks the *referencing* entity also as `STEP_LOAD_ERROR` and emits a single `WARNING: <name> is not valid` to `bu_log`. But the upstream caller does **not** check `entity_status` for the shells/solids it consumes; the shape-definition path completes with whatever fragments it managed to build, and the resulting .g file lacks the entire subgraph that depended on the broken reference. On large assemblies the user only notices the truncation after a multi-minute import; the diagnostic stream is too noisy to spot the specific WARNING line.

Reproducer recipe

STEP file containing a topology entity that references id `#999` which is never defined. Pass-1 instantiates the entity; pass-2 sets `STEP_LOAD_ERROR`; the parent shape is silently truncated.

Expected kernel behavior

reject; every shell/solid consumer in `LoadONBrep` must consult `entity_status` of every dereferenced child and bubble up `STEP_LOAD_ERROR`; the top-level converter must abort with a non-zero exit code rather than write a partial .g file.
