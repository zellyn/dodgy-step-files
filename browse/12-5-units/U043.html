U043 — Slicer-side unit-context inversion: STEP says mm, slicer reads as inches

§12.5 units & coordinate systems

P1 — silent data loss

units

View raw fixture (.stp) step-examples/12-5-units/U043.stp

Sources

  • FreeCAD #18078 (related)
  • bug-reporter language: "STEP file marked inch but the model scales up in size", "model is 25.4× too big after import", "unit declaration inverted on receiver side".

Sender

STEP-receiving slicers that auto-detect unit by comparing `LENGTH_UNIT` declaration against a hard-coded "expected mm" assumption and silently flip when the file has an explicit `INCH` declaration.

Description

A producer-side STEP correctly declares `INCH` units with inch-scale numerical values. A receiver that hard-codes "STEP files are mm" silently treats the inch values as mm — yielding a 25.4× too-small model. Mirror image of Wr044. The on-disk file is well-formed; the bug is that some slicer lineage assumes mm regardless of the declared unit context.

Reproducer recipe

STEP file with `LENGTH_UNIT` complex record `(LENGTH_UNIT() NAMED_UNIT(*) CONVERSION_BASED_UNIT('INCH', ..))` and `CARTESIAN_POINT` corner coordinates `(1.0, 1.0, 1.0)` (one inch — should appear as 25.4 mm to a correct receiver).

Expected kernel behavior

Heal and accept: receivers MUST honour the declared `LENGTH_UNIT` context, normalize coordinate values into the kernel's canonical unit, and never assume mm without inspecting it. Reject with E_UNIT_CONTEXT_IGNORED if the unit declaration cannot be parsed; treating inch-tagged data as millimetres without diagnostic is a coverage gap.

Notes

**See also**: U015, Wr044. Synonyms: "slicer ignores STEP unit declaration", "INCH unit silently treated as mm by receiver", "unit-context inversion on receiver side".
