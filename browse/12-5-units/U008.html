U008 — NX subassemblies with mixed inch + mm — inconsistent per-part scaling

§12.5 (sub-class: mixed-unit / assembly)

  • 10-vendor-kbs.md V049 (assembly STEP scale mismatch)

Sender

any sender mixing inch and mm subassemblies

Description

STEP files with mixed inch and mm contexts in subassemblies cause inconsistent scaling: inch parts multiplied by 25.4, metric parts not, leading to mis-scaled assembly.

Reproducer recipe

AP242 assembly with one component's `GEOMETRIC_REPRESENTATION_CONTEXT` declaring inch (via `CONVERSION_BASED_UNIT('INCH',..)`) and another declaring `SI_UNIT(.MILLI.,.METRE.)`, joined via `MAPPED_ITEM` whose `mapping_source` carries no scale.

Expected kernel behavior

Heal and accept: normalize / apply unit context per child sub-representation; never assume a document-wide unit; coerce / scale at `MAPPED_ITEM` / sub-assembly boundary using each child's own `GEOMETRIC_REPRESENTATION_CONTEXT` global units.

Notes

Cross-oracle: pure-Python Part-21 validator accepts (`accept`); OCCT crashes (`signal(11)`). The crash is on the kernel side; the file is spec-conformant Part-21. Synonyms: "NX assembly mixed inch and mm parts", "subassembly inch parts scale wrong vs mm", "MAPPED_ITEM cross-context unit mixing", "STEP assembly inconsistent unit scaling", "mixed inch+mm assembly mis-scales".

Expected validation

occt=signal(11)/signal(11) gmsh=signal(11) ifc=schema_n/a

Byte assertions

  • contains(b"CONVERSION_BASED_UNIT('INCH'") and contains(b'.MILLI.')
  • count_entity_def(b'GEOMETRIC_REPRESENTATION_CONTEXT') >= 2 or contains(b'MAPPED_ITEM')
