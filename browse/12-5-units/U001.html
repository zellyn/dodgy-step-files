U001 — Solid Edge mm exported STEP read as meters by Inventor (imported part 1000 times bigger than expected)

§12.5 (sub-class: wrong-declaration / receiver-side defaulting)

silent-loss units

View raw fixture (.stp) step-examples/12-5-units/U001.stp

Sources

  • 10-vendor-kbs.md V001 (forums.autodesk.com t5/inventor-forum/step-file-units-are-messed/td-p/619614)

Sender

Solid Edge (mm)

Description

STEP written from Solid Edge with `LENGTH_UNIT() NAMED_UNIT(*) SI_UNIT(.MILLI., .METRE.)` plus a small `UNCERTAINTY_MEASURE_WITH_UNIT` (e.g. 0.001 mm) and coordinates in mm (e.g. 100×50 mm extents) is interpreted by Inventor as base SI (metre), giving an imported part 1000 times bigger than expected after the unit conversion. The receiver ignores the producer's `LENGTH_UNIT` context (and any auxiliary `DIMENSIONAL_EXPONENTS` instance) and defaults to base SI.

Reproducer recipe

`GEOMETRIC_REPRESENTATION_CONTEXT` whose units list contains `(LENGTH_UNIT() NAMED_UNIT(*) SI_UNIT(.MILLI., .METRE.))`; coordinates encoded as raw mm; reader that strips the prefix and treats the number as metres.

Expected kernel behavior

reject default-to-base; honour `SI_UNIT.prefix`; never silently rescale because the reader expected another unit.

Notes

**See also**: U002, U003, U015. **OCC behavior**: silently accepts the millimetre-prefixed file with no scale-mismatch diagnostic. The surrounding tooling pipeline is what mis-reads; the catalog above forbids silent rescaling. Synonyms: "Solid Edge mm imported as meters 1000x bigger", "Inventor reads STEP mm as metres", "STEP imported 1000 times too large", "mm prefix ignored on STEP import", "MILLI METRE silently treated as METRE".

Expected validation

occt=empty/empty gmsh=empty ifc=schema_n/a

Byte assertions

  • contains(b'SI_UNIT(.MILLI.,.METRE.)') or contains(b'SI_UNIT(.MILLI., .METRE.)')
  • matches(rb'GEOMETRIC_REPRESENTATION_CONTEXT|REPRESENTATION_CONTEXT')

Tier-3 assertions

  • shape_null == True
