Tsh246 — Two face-hosted candidate edges of unequal length: the longer becomes the parametrization reference

Sources

  • occt-coverage PARTIAL audit, `exchange/problems.json` `sew-longest-edge-reference-selection` (`BRepBuilderAPI_Sewing::SameParameterEdge`, `BRepBuilderAPI_Sewing.cxx:573-591`). N148 (the sole existing fixture) presents the same 5.0-vs-4.9mm length pattern but as a faceless `GEOMETRIC_CURVE_SET` (floating-mode-only, authored for `EvaluateDistances` projection, not reference selection) — every face-based merge fixture in the corpus (Twi037, Tfa019, Tfa020, Tsh203, M045) pairs equal-length edges, leaving the length-based reference choice unobservable on real face-hosted geometry.

Description

An `OPEN_SHELL` with TWO `ADVANCED_FACE`s. Face LONG hosts a 5.0mm free edge x:[0,5],y=0. Face SHORT hosts a 4.9mm free edge x:[0.05,4.95],y=1e-4 — a within-tolerance gap, SHORT's endpoints both strictly interior to LONG's parametric span, comfortably above the `sew-free-edge-gap-merge` min-length floor. `SameParameterEdge`, on its first (top-level) call, computes both candidates' 3D curve length via arc-length evaluation and assigns the LONGER edge's parametrization as the retained merge reference.

Reproducer recipe

Two real, face-hosted, unequal-length (e.g. 5.0mm vs 4.9mm) near-coincident free edges within sewing tolerance, the shorter one's endpoints strictly interior to the longer one's span (N148's length pattern rebuilt on real `ADVANCED_FACE`s instead of a `GEOMETRIC_CURVE_SET`).

Expected kernel behavior

on merge, retain the LONGER candidate edge's 3D curve and parametrization as the authoritative reference, re-projecting the shorter edge's contribution onto it, rather than arbitrarily picking whichever edge was passed first.

Notes

Live-verified (this worktree's OCP/OCCT 7.8.1, runtime the sewing stage(tolerance=1.0)` scaffold): after sewing, `NbContigousEdges()==1` (clean single merge); the resulting shared edge's `BRep_Tool::Range` is exactly `(0.0, 5.0)` — LONG's own original parameter range — not SHORT's `(0.0, 4.9)`, directly confirming LONG's parametrization/curve identity survived as the merge reference. The two candidates' VERTEX endpoints DO get tolerance-averaged to `(0.025, 4.975)` — a distinct, separately-cataloged mechanism (`sew-edge-endpoint-tolerance-reconciliation`), not this class; the load-bearing assertion is the retained parameter-range/curve identity, which the vertex averaging does not disturb. Synonyms: "longest edge becomes sewing reference", "SameParameterEdge length comparison", "unequal-length edge merge parametrization", "shorter edge reprojected onto longer", "arc-length evaluation reference selection".
