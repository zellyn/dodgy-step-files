Tsh251 — Face-hosted gap candidate whose achieved merge tolerance exceeds a caller-declared cap: the merge is nullified, not returned out-of-spec

Sources

The class's base accept-and-tighten behavior is already exercised by the corpus's existing gap fixtures, but none of the three named subvariants (swapped-reference retry, a cruder last-resort tolerance estimate, and a hard cap with nullify-on-exceed) had live confirmation — the closest prior attempt is a faceless, non-face-hosted scaffold whose decisive values exist only in file comments, unreachable by a passive loader.

Description

Two real `ADVANCED_FACE`s in one `OPEN_SHELL`: Face A hosts a 5.0mm free edge, Face B hosts a matching 5.0mm free edge offset by a genuine 0.05mm gap — comfortably inside the sewing tolerance, so the pair merges and reports an achieved tolerance proportional to the true gap. The same candidate pair, sewn again with a caller-declared tolerance cap set below that achieved value, is instead left entirely unmerged.

Reproducer recipe

`OPEN_SHELL` with two `ADVANCED_FACE`s, Face A's free edge x:[0,5],y=0 and Face B's free edge x:[0,5],y=0.05 (both length 5.0mm, gap 0.05mm).

Expected kernel behavior

accept a merge whose residual mismatch fits within a tolerance budget derived from the edge's own tolerance and the curves' precision, tightening the resulting edge's reported tolerance to the actual achieved mismatch; if a caller-declared maximum tolerance is exceeded even after that acceptance, treat it as a hard backstop and drop the merge entirely rather than return an edge whose reported tolerance is out of the caller's declared spec.

Notes

Live-verified (this worktree's OCP/OCCT 7.8.1, runtime sewing scaffold): with the operator's own cap left at its shared default, the pair merges cleanly (`NbContigousEdges()==1`), the shared edge's achieved tolerance comes back `0.0525` (gap-proportional). Re-run against the IDENTICAL geometry with an explicit tolerance cap of `0.01` (below the `0.0525` the merge would otherwise achieve) declared before the merge runs, the SAME candidate pair is instead rejected outright — `NbContigousEdges()==0`, `NbFreeEdges()==6`, both original edges remain unmerged at their default tolerance — a directly observable, reproducible before/after contrast confirming the cap nullifies the merge rather than returning an out-of-spec edge. The default STEP-read path itself does not invoke this merge mechanism at all (both healing settings report the identical, unmerged 2-face shape); the cap behavior is exercised purely by the sewing operator at verification time. Synonyms: "sewing tolerance cap nullify", "merge exceeds max tolerance rejected", "hard tolerance backstop sewing", "candidate merge dropped over cap", "tolerance budget acceptance sewing".
