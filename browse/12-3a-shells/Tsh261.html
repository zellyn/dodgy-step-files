Tsh261 — Two hanging vertices project onto the same interior stretch of one boundary edge a hair's breadth apart: only one cut node is created

Sources

  • occt-coverage PARTIAL audit, `exchange/problems.json` `sew-cutting-hanging-vertex-split` subvariant "snap-to-existing-cut-vertex vs create-new-cut-vertex threshold" (`BRepBuilderAPI_Sewing::CreateCuttingNodes`, `BRepBuilderAPI_Sewing.cxx:4449-4481`: `if (distMin <= Max(disProj*0.1, MinTolerance()))` binds the projected point to the existing cutting/endpoint vertex, otherwise a brand-new cutting vertex is built and inserted into the parameter-ordered sequence). Companion to Tsh260, which demonstrates the base T-junction split but has both hanging vertices far apart, so only the create-new branch fires there.

Description

An `OPEN_SHELL` with THREE planar triangular `ADVANCED_FACE`s. Face LONG (plane z=0) carries the reference `EDGE_CURVE` running x=1, y:[0,2] (apex off at (-3,1,0)). Face UP (plane z=+0.4) has a vertex at (1,0.9,0.4) hanging 0.4 above the reference edge's interior, plus an edge from (1,0.9,0.4) to (1,2,0.4) running parallel to the reference edge. Face DOWN (plane z=-0.4) has a vertex at (1,0.92,-0.4) hanging 0.4 below the reference edge. Both hanging vertices project onto the SAME reference edge, at y=0.9 and y=0.92 — 0.02 apart, i.e. inside 10% of their own 0.4 projection distance. Putting them on OPPOSITE sides of the reference edge is what makes the case reachable: the two vertices are 0.8 apart, more than the 0.6 sewing tolerance, so the tolerance-driven vertex gluing that precedes the split leaves them as two distinct nodes, while both still project onto the same tiny stretch of the edge. No pcurves; 3D-`EDGE_CURVE`-only convention as in Tsh260.

Reproducer recipe

`OPEN_SHELL` with three planar triangular `ADVANCED_FACE`s: one hosting a long straight `EDGE_CURVE` (x=1, y:[0,2], z=0); a second, offset +0.4 in z, whose first vertex hangs over that edge's interior at y=0.9 and whose first edge runs parallel to it spanning y:[0.9,2.0]; a third, offset −0.4 in z, whose first vertex hangs under the same edge at y=0.92. Sew at tolerance 0.6 (both hanging vertices within tolerance of the reference edge, the two vertices 0.8 apart so they are not glued to each other).

Expected kernel behavior

when the shape is passed through the standard shell-sewing pass, the first hanging vertex creates a cut node at its projection (y=0.9) and the second, whose projection is a hair's breadth away (0.02, within 10% of its own 0.4 projection distance), is bound to that same node instead of producing a redundant second cut 0.02 further along; the reference edge is therefore replaced by exactly TWO collinear sub-edges, not three, and the upper section stays span-matched to Face UP's parallel edge so the boundary is genuinely conformalized.

Notes

Why we believe this test is valid — RUNTIME-SCAFFOLD verified against this fixture's own bytes (this worktree's `validation/.venv`, OCP/OCCT 7.8.1). `STEPControl_Reader.ReadFile` → `TransferRoots` loads shape_null=False with 3 faces and 9 unique edges (`TopTools_IndexedMapOfShape`), the reference edge `[(1,0,0),(1,2,0)]` intact. Feeding the read shape to `BRepBuilderAPI_Sewing(0.6, sew=True, analysis=True, cutting=True, nonmanifold=False)` and calling `Perform()` replaces the reference edge with exactly TWO collinear sub-edges — `[(1,0,0),(1,0.9,·)]` and `[(1,0.9,·),(1,2,·)]` — cut ONLY at y=0.9. There is no cut at y=0.92: the second hanging vertex was snapped onto the node the first created. `NbContigousEdges()==1` (the upper section merges with Face UP's parallel edge), `NbMultipleEdges()==0`. Threshold sweep on the DOWN vertex's y (its projection distance held at 0.4, so the predicted flip is at 0.1×0.4 = 0.04): y=0.90 / 0.92 / 0.935 / 0.939 / 0.9400 all give `NbContigousEdges()==1`; y=0.9401 / 0.941 / 0.945 / 0.96 / 1.00 all give `NbContigousEdges()==0` — past the threshold a redundant second cut appears at the second vertex's own projection, the reference edge is split into three sections, none matches Face UP's span, nothing merges, and the conformalization is lost. The flip is exactly at 0.0400 → 0.0401, matching `disProj*0.1` to four digits. Sewing is NOT on the default STEP read path (a default read leaves both T-junctions non-conformal), so this fixture is oracle-invisible to the shape-count oracle and requires the sewing scaffold to observe. Synonyms: "two hanging vertices same edge one cut node", "redundant cut vertex suppressed sewing", "adaptive snap tolerance projected node STEP", "CreateCuttingNodes snap to existing cutting vertex", "T-junction near-duplicate projection conformalize".
