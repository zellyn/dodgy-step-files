Sw007 — Fast-sewing cannot find the canonical vertex for a wire endpoint

§12.3a (sub-class: fast-sewing vertex-table miss)

Description

While building the fast-sewing vertex table, a wire endpoint hashes to a bucket containing only vertices at very different 3D coordinates — no near-coincident match within the sewing tolerance. The algorithm cannot decide whether to dedup or insert. Typical fixture: two VERTEX_POINTs with widely separated coordinates (e.g., (0,0,0) and (1e6,0,0)) that nonetheless share a hash bucket. Bug-reporter language: "fast sew vertex hashing mismatch", "vertex not found", "widely-separated VERTEX_POINTs collide in hash".

Reproducer recipe

Two VERTEX_POINTs whose 3D coordinates differ by a large magnitude (e.g., (0,0,0) and (1e6,0,0)) that, due to the underlying float bit pattern, fall into the same hash bucket but are spatially distant — possibly with no edges or shells defined.

Expected kernel behavior

Heal and accept: normalize with spatial hashing under tolerance, not bit-equal hashing; fall back to the slow path.

Notes

Rare; depends on hash function used. Provenance tier: runtime-only — bytes alone cannot demonstrate this defect; the symptom is a hash-bucket collision inside the fast-sewing vertex table during a sewing operation. The static fixture encodes only the inputs; whether they collide depends on the kernel's specific hash function and table size. A behavioral test against the sewing implementation is the appropriate venue. Synonyms: "fast sew vertex hashing mismatch", "vertex not found", "widely-separated VERTEX_POINTs collide in hash", "hash bucket collision in vertex table", "spatial hash needed instead of bit-equal".
