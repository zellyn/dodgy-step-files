Ps014 — Position tolerance frame cites datum compartments in wrong order

§12.3a shells / orientation (filed here per Ps prefix; conceptually §12.7 PMI)

Sources

  • deduced from DATUM_REFERENCE_COMPARTMENT order semantics
  • bug-report patterns "GD&T datum order wrong", "PMI compartments swapped", "primary/secondary/tertiary mixed up"

Description

A block with three labeled DATUM_FEATUREs (A on bottom, B on front, C on left). The producer intended a position tolerance |⌖|0.05|A|B|C|. Due to a list-ordering bug in the PMI exporter, the DATUM_SYSTEM lists compartments in order (A, C, B). The schema accepts any order; the tolerance is mathematically valid but yields a different inspection regime; secondary and tertiary roles swap, so the constraint axes the gauge uses are different.

Reproducer recipe

A 10x10x10 block with three DATUMs (A, B, C) mapped to bottom/front/left faces via three GISUs. A POSITION_TOLERANCE attached to a DATUM_SYSTEM whose datum_constraints list is (A_compartment, C_compartment, B_compartment).

Expected kernel behavior

A kernel cannot detect a "wrong order" without knowing the producer's intent, but it can surface the ordered list of (datum-letter, compartment-role) tuples per tolerance so downstream PMI tools can validate against the drawing's drawing- number-keyed expected order. A correct kernel should not normalize compartment order silently.

Notes

Tier-3 metric: list of (tolerance, [(datum_letter, compartment_index)]) tuples. Cross-checked against an external drawing-of-record to flag swaps. Synonyms: "GD&T datum order wrong", "PMI compartments swapped", "primary secondary tertiary mixed up", "datum reference frame in wrong order", "position tolerance datums out of sequence".

Expected validation

occt=shape(1)/shape(1) gmsh=shape(27) ifc=schema_n/a

Tier-3 assertions

  • n_edges_total >= 24
  • face[0].surface_type == "plane"
  • face[5].surface_type == "plane"
