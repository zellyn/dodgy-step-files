Gn038 — `BOUNDED_PCURVE` LoadONBrep stub (BRL-CAD step-g)

§12.2b NURBS/knots (sub-class: subtype unimplemented)

P1 — silent data loss

geometry

View raw fixture (.stp) step-examples/12-2b-nurbs/Gn038.stp

Sources

  • BRL-CAD `src/conv/step/step-g/Curve.cpp` `LoadONBrep` base stub `"::LoadONBrep(..) not implemented for <entity>"`
  • `BoundedPCurve` is a non-overriding subclass that inherits the stub
  • bug-reporter language: "BOUNDED_PCURVE dropped on import", "step-g subtype unsupported", "BOUNDED_PCURVE falls through to base-class stub".

Sender

Producers that emit a bounded re-parametrisation of an otherwise infinite parametric basis curve.

Description

`BOUNDED_PCURVE` is a degenerate subclass whose role is to give a bounded version of an otherwise infinite parametric basis curve. step-g loads the entity into the in-memory model fine, but the LoadONBrep path falls through to the base-class stub which prints `"not implemented for BoundedPCurve"` and returns false. Trims referencing a `BOUNDED_PCURVE` in their `associated_geometry` list lose the parametric curve in the ON_Brep representation, so the trim becomes 3D-only and is later re-projected numerically (introducing drift). Distinct from Gn019 (coincident-control-point degeneracy): this is a *type-dispatch* defect rather than a degeneracy.

Reproducer recipe

`#41=BOUNDED_PCURVE('bp_on_plane', #14, #40);` referenced from a `SURFACE_CURVE.associated_geometry`. step-g loads the entity; LoadONBrep stub returns false.

Expected kernel behavior

heal-and-accept — `BoundedPCurve::LoadONBrep` must defer to its underlying definitional basis curve and reparameterise to the bounded subrange; if unhandled, emit `W_BOUNDED_PCURVE_FALLBACK` and project from 3D.

Notes

**See also**: Gn019, Twi100, Twi101. Synonyms: "BOUNDED_PCURVE LoadONBrep stub", "step-g BOUNDED_PCURVE drop", "BOUNDED_PCURVE subtype unimplemented".
