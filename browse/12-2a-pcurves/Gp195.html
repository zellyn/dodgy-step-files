Gp195 — Composite curve whose segments are listed out of connected order, in the container where the reorder repair is observable

Sources

  • occt-coverage `exchange/problems.json` `stp-compcurve-reorder` (`StepToTopoDS_TranslateCompositeCurve::Init`, `StepToTopoDS_TranslateCompositeCurve.cxx:265-274` — `sfw->FixReorder()`, and `StatusReorder(ShapeExtend_DONE)` → the warning "Segments were disordered
  • fixed"). The verdict was held at PARTIAL because Gp176 could not be made to show the repair firing. Root cause identified live: Gp176 hands its composite curve to an `EDGE_CURVE` as `edge_geometry`, which routes through the single-curve conversion path and never constructs the segment-wise wire assembler at all (Gp176 reports " Make Geom_Curve (3D) failed" / "Could not convert a curve", and no reorder message, in either segment order). The assembler — and hence the reorder pass — is only reached when the composite curve is an ELEMENT of a curve set (`StepToTopoDS_Builder::Init(GeometricSet)`, `StepToTopoDS_Builder.cxx:677-698`).

Description

A `COMPOSITE_CURVE` traces the unit square with four `COMPOSITE_CURVE_SEGMENT`s, but lists them A, C, B, D — the top edge sits between the bottom edge and the right edge, so successive entries in the list do not follow on from one another, and the permutation is neither the identity nor a cyclic rotation (which on a closed wire would be a mere choice of starting point). Every segment's parent curve is a genuinely BOUNDED curve — a degree-1 `B_SPLINE_CURVE_WITH_KNOTS` over a finite [0,1] domain — so each yields a real finite edge, unlike the infinite-parameter segments a bare `LINE` produces. The composite curve is the sole element of the shape representation's own curve set, so it is a real translation root, not an orphan.

Reproducer recipe

four `B_SPLINE_CURVE_WITH_KNOTS` of degree 1, knots `(0.0,1.0)`, multiplicities `(2,2)`: `seg_a_bottom` (0,0,0)→(1,0,0), `seg_b_right` (1,0,0)→(1,1,0), `seg_c_top` (1,1,0)→(0,1,0), `seg_d_left` (0,1,0)→(0,0,0); each wrapped in `COMPOSITE_CURVE_SEGMENT(.CONTINUOUS.,.T.,#crv)`; then `COMPOSITE_CURVE('composite_curve_scrambled_order',(#seg_a,#seg_c,#seg_b,#seg_d),.F.)` — note the A, C, B, D order — inside `GEOMETRIC_CURVE_SET('gp195_composite_set',(#composite))` in a `MANIFOLD_SURFACE_SHAPE_REPRESENTATION`.

Expected kernel behavior

detect that the segment list is not in connected sequence, reorder the collected segments algorithmically before assembling them, log that the disorder was repaired, and emit a single wire — rather than building a disjoint or self-crossing wire in list order.

Notes

**See also**: Gp176 (byte-genuine disordered composite curve in the container where the repair cannot be observed — this entry is its observable counterpart, not a duplicate), Twi007, Twi028, Twi038 (`EDGE_LOOP` edge-list scrambles, a different translation path), Ad137, Gp188 (composite-curve siblings). Live-verified (2026-07-31, this worktree, OCP/OCCT 7.8.1): the transfer check list carries exactly one message, the warning "Segments were disordered; fixed" — the literal string emitted when the reorder status comes back set — and the transfer yields ONE wire of 4 edges (8 raw vertices). Perturbation control (byte-level A/B): re-listing the same four unchanged segment entities in their connected order A, B, C, D — a single-token edit to the segment list, nothing else — makes the warning disappear entirely while the resulting topology is identical (1 wire, 4 edges, 8 vertices, zero check messages). The message is therefore caused by the segment ORDER alone, which is exactly what Gp176's own control could not establish, because in Gp176's configuration both orders produced the identical empty signature. Synonyms: "segments were disordered fixed", "composite curve segments out of sequence", "composite curve reorder", "successive segments do not follow on", "wire assembled from scrambled segments".
