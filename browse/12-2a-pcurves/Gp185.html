deduced — OCCT uncovered-class sweep, work packet D2.

Description

A unit-radius `CYLINDRICAL_SURFACE` carries a self-closed full-circle `EDGE_CURVE` (start==end vertex) whose 3D `CIRCLE` is a correct, single physical revolution — but whose `PCURVE` is a 2D `LINE` running from `u=0` to `u=40*pi` (20 full periods) instead of the correct single period `[0, 2*pi]`. This is the "degree-vs-radian confusion" signature named in the class description: a parametric span vastly exceeding the surface's actual angular domain, not merely a single-period offset (contrast Gs007/Gp023, which are single-period shifts exercising a different repair path).

Reproducer recipe

`CYLINDRICAL_SURFACE` radius 1; self-closed full-circle `EDGE_CURVE`; `PCURVE` 2D `LINE` from `(0,0)` with direction `(1,0)` and vector magnitude `40*pi` (≈125.6637) instead of `2*pi`.

Expected kernel behavior

`XSAlgo_AlgoContainer::CheckPCurve` detects the multi-period span and drops the pcurve, recomputing a correctly-bounded one.

Notes

**See also**: Gs007, Gp023 (single-period-shift subvariant, different repair path), Gp022 (a different pcurve-consistency mechanism: same-parameter deviation, not span). **Empirical finding (live-verified, decisive)**: `BRep_Tool::Range(edge, face)` on the translated shape reads back `(0.0, 6.283185307179586)` — exactly one period (`2*pi`), NOT the authored `(0.0, 125.66...)`. Verified identically under `read.surfacecurve.mode` 0 (3D-preferred) and 3 (pcurve-preferred, `occt_heal_on`'s own setting). This is a genuine, decisive live confirmation that the cited mechanism (multi-period span detected, pcurve dropped, a correct one recomputed) fires on this exact input during ordinary STEP import — the file's declared 20-period pcurve never survives to the final shape; the class's own description ("drops the pcurve") is exactly what is observed.
