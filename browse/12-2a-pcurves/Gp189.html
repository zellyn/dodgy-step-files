Description

A half-cylinder face (u in `[0,pi]`, v in `[0,1]`), the same 4-edge idiom as Gp035. The left seam edge's `SURFACE_CURVE` carries a correct 3D `LINE` plus a real, non-null `PCURVE` in `associated_geometry` — but that `PCURVE`'s `DEFINITIONAL_REPRESENTATION` `items` list references a `LINE` built from 3-coordinate (3D) `CARTESIAN_POINT`/`DIRECTION` entities instead of the 2-coordinate ones a pcurve's UV-space `LINE` requires — a wrong-dimensionality item, the kind of bug a producer's export code genuinely commits when it accidentally wires a 3D curve builder into a 2D pcurve slot. The other three edges (bottom arc, right seam, top arc) are correct `SURFACE_CURVE`s.

Reproducer recipe

Left seam `SURFACE_CURVE` wraps a correct 3D `LINE` plus one `PCURVE` whose `DEFINITIONAL_REPRESENTATION` item is `LINE('wrong_dim_pcurve_item', <3D point>, <3D vector>)` instead of a 2D `LINE`.

Expected kernel behavior

the malformed pcurve item fails its per-item conversion; the edge-loop translation stage defers the edge and computes a correct pcurve by projecting the already-built 3D edge onto the face's surface.

Notes

**See also**: Gp001, Gp035, Gp042 (the "no pcurve entity at all" trigger mode — already solid). Gp012 (struck as a bogus citation for this class per prior audit: its `SEAM_CURVE associated_geometry` contains `(#pc,$)`, a null `$` slot, which is the SAME "absent pcurve" mode as Gp001/Gp035/Gp042, not "a real pcurve reference that fails to translate"). This fixture is the first to encode the latter. **Empirical finding (live-verified, decisive; includes a discarded unsafe attempt)**: the obvious first construction — a `DEFINITIONAL_REPRESENTATION` item that is a totally wrong entity TYPE (a bare `CARTESIAN_POINT` standing in for a curve) — was built and tested first. It reads and transfers-roots without a caught Python exception, but SEGFAULTS OCCT 7.8.1 (OCP) once that malformed edge sits inside a closed 4-edge loop next to other pcurve'd edges (confirmed reproducible: a single-edge, non-looped minimal repro of the identical item does NOT crash; the same item inside a 4-edge closed loop crashes 100% of the time, under both `healing=True` and `healing=False`). A segfault is not a Python-catchable outcome — it kills the interpreter — so that construction was DISCARDED as unsafe for this corpus's live harness/CI and never shipped. The wrong-dimensionality `LINE` shipped here was verified safe (no crash under either healing profile) and, via `BRep_Tool::CurveOnSurface` on the translated shape, decisively confirmed to demonstrate the intended mechanism: the left seam edge's malformed pcurve item is silently dropped, and OCCT supplies a freshly-computed pcurve instead — sampled at `t=0.0,0.25,0.5,0.75,1.0`, the recovered pcurve is `u=0.0` constant with `v` running `0.0→1.0`, exactly the correct projected result for that physical edge (matching the healthy right-seam edge's own pcurve shape in Gp035).
