M134 — AP203 two distinct PERSON entities share the same id

§12.8 (sub-class: AP203 identifier collision)

P1 — silent data loss

spec-violation

View raw fixture (.stp) step-examples/12-8-mixed/M134.stp

Sources

  • 16-iso-spec ISO 10303-41 (person uniqueness in approval)
  • bug-reporter language: "AP203 PERSON id collision", "two people same identifier", "PDM approver ambiguous".

Sender

deduced — PDM exporter that pulled PERSON records from two source databases without re-mapping identifiers

Description

Two `PERSON` instances declare the same identifier (e.g. 'jdoe') yet have different last names ('Doe' vs 'Doppelganger'). PERSON.id is intended to uniquely identify the individual across the design pool; this collision makes downstream APPROVAL_PERSON_ORGANIZATION references ambiguous about which individual approved.

Reproducer recipe

`PERSON('jdoe','Doe','John',..)` and `PERSON('jdoe','Doppelganger','Jane',..)` in the same file.

Expected kernel behavior

detect duplicate PERSON.id; reject or warn. Auto-rename is out of scope.

Notes

Synonyms: "AP203 person ID conflict", "PDM identifier collision", "approver disambiguation".

Expected validation

occt=empty/empty gmsh=empty ifc=schema_n/a

  • contains(b"PERSON('jdoe',")
