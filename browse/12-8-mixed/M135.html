M135 — AP203 declares CONFIG_CONTROL_DESIGN (CC1) but uses CC2-only entities

§12.8 (sub-class: AP203 schema-version mismatch)

P1 — silent data loss

spec-violation

View raw fixture (.stp) step-examples/12-8-mixed/M135.stp

Sources

  • 16-iso-spec ISO 10303-203 Ed.1 vs Ed.2 (CC1 / CC2 schema delta)
  • bug-reporter language: "AP203 CC1 with CC2 entities", "CONFIG_CONTROL_DESIGN strict reader rejects DESIGN_CONTEXT".

Sender

deduced — PDM exporter that switched its protocol header to CC1 (legacy compatibility) without filtering out CC2-only entities

Description

A file declares the legacy `CONFIG_CONTROL_DESIGN` schema in its `FILE_SCHEMA` yet uses entities such as `DESIGN_CONTEXT` and `MECHANICAL_CONTEXT` that were introduced in the AP203 second- edition (CC2 / CCD2) schema. CC1-strict readers reject the unknown entities; lax readers accept and produce inconsistent results.

Reproducer recipe

`FILE_SCHEMA(('CONFIG_CONTROL_DESIGN'))` with `DESIGN_CONTEXT` / `MECHANICAL_CONTEXT` instances in DATA section.

Expected kernel behavior

warn on schema-version mismatch; either upgrade the declared schema to CC2 or strip the CC2-only entities and reject if neither is acceptable.

Notes

Synonyms: "AP203 schema version mismatch", "CC1/CC2 mix", "legacy schema with newer entities".

Expected validation

occt=empty/empty gmsh=empty ifc=schema_n/a

Byte assertions

  • contains(b'CONFIG_CONTROL_DESIGN')
  • contains(b'DESIGN_CONTEXT')
  • contains(b'MECHANICAL_CONTEXT')
