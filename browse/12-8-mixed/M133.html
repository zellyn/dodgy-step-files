M133 — AP203 inconsistent ISO 8601 date formats within the same file

§12.8 (sub-class: AP203 date format consistency)

P1 — silent data loss

spec-violation

View raw fixture (.stp) step-examples/12-8-mixed/M133.stp

Sources

  • 16-iso-spec ISO 10303-203 §5.7 (date_and_time / timezone)
  • bug-reporter language: "STEP dates inconsistent timezone", "AP203 mixed date format", "naive timestamp in PDM file".

Sender

deduced — PDM exporter merging timestamps from two systems with different timezone-handling conventions

Description

One `DATE_AND_TIME` in the file captures a `LOCAL_TIME` with no `COORDINATED_UNIVERSAL_TIME_OFFSET` (timezone-naive); another in the same file uses an explicit UTC offset. Comparing the two requires assuming a timezone for the naive value. Bug-reporter language: "AP203 timezone mismatch", "STEP timestamp naive vs aware".

Reproducer recipe

`DATE_AND_TIME(..,LOCAL_TIME(14,30,0.0,$))` and `DATE_AND_TIME(..,LOCAL_TIME(14,30,0.0, COORDINATED_UNIVERSAL_TIME_OFFSET(0,0,.AHEAD.)))` in the same file.

Expected kernel behavior

warn on mixed timezone-aware / timezone-naive timestamps; or reject. Should not silently compare.

Notes

Synonyms: "AP203 date format inconsistent", "naive vs aware timestamp", "timezone-mixing".

Expected validation

occt=empty/empty gmsh=empty ifc=schema_n/a

Byte assertions

  • contains(b'CONFIG_CONTROL_DESIGN')
  • count_entity_def(b'DATE_AND_TIME') >= 2
  • contains(b'COORDINATED_UNIVERSAL_TIME_OFFSET')

Tier-3 assertions

  • shape_null == True
