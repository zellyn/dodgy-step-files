Xp036 — STYLED_ITEM colours dropped by bare STEPControl_Reader (vs XCAF reader)

§12.12 cross-product (appearance × receiver reader choice)

P1 — silent data loss

round-trip interop

View raw fixture (.stp) step-examples/12-12-cross-product/Xp036.stp

Sources

  • github.com/CadQuery/cadquery issue #1638 "Problem importing STEP with colours"
  • CadQuery discussion #1454 "combine colored step files"
  • bug-reporter language: "imported STEP files always appear yellow", "colours visible in viewer X but not in Y".

Sender

any STEP file with valid STYLED_ITEM presentation graph

Description

STYLED_ITEM, MECHANICAL_DESIGN_GEOMETRIC_PRESENTATION_REPRESENTATION, COLOUR_RGB and the PRESENTATION_STYLE_ASSIGNMENT chain live in a parallel forest of presentation entities not reachable from the MANIFOLD_SOLID_BREP root. STEPControl_Reader walks only geometry; XCAF (STEPCAFControl_Reader) walks both. CadQuery historically exposed only the bare reader, so colours appeared yellow / default after import even though they were correctly written.

Reproducer recipe

ADVANCED_FACE with COLOUR_RGB(1.0, 0.0, 0.0) bound via STYLED_ITEM and MECHANICAL_DESIGN_GEOMETRIC_PRESENTATION_REPRESENTATION. The presentation forest is not referenced from MANIFOLD_SOLID_BREP, so a depth-first walk from the solid root never sees it.

Expected kernel behavior

kernels exposing a high-level "load STEP" API must default to the XCAF-aware path; bare-geometry reads must surface a "presentation entities ignored" warning so users know colours were dropped.

Notes

**See also**: Xp034, Xp035. Synonyms: "STYLED_ITEM ignored on import", "STEP colours appear yellow", "bare reader skips presentation", "STEPControl_Reader vs STEPCAFControl_Reader", "colour metadata lost on load".

Expected validation

occt=empty/empty gmsh=empty ifc=schema_n/a

Byte assertions

  • contains(b'MECHANICAL_DESIGN_GEOMETRIC_PRESENTATION_REPRESENTATION')
  • contains(b'STYLED_ITEM')
