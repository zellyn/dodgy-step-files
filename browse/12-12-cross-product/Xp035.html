Xp035 — CadQuery STEP writer emits redundant COLOUR_RGB entities for identical colours

§12.12 cross-product (writer optimisation × file size)

interop

View raw fixture (.stp) step-examples/12-12-cross-product/Xp035.stp

Sources

  • github.com/CadQuery/cadquery issue #1689 "Exporting STEP with colors doesn't de-duplicate as expected with different, but same-valued Colors"
  • bug-reporter language: "the same gray appears 200 times in the file", "STEP writer doesn't pool identical colours".

Sender

CadQuery STEP writer

Description

The writer emits one fresh COLOUR_RGB entity per (object, color) tuple, even when many tuples share the same RGB value. The result is hundreds of entities like COLOUR_RGB('',0.5,0.5,0.5) that should be a single shared instance. File size bloats; receivers that pool colours on import end up with N "different" colours that all happen to have value (0.5, 0.5, 0.5).

Reproducer recipe

three COLOUR_RGB entities all carrying (0.5, 0.5, 0.5); three FILL_AREA_STYLE_COLOURs each referencing one; three SURFACE_STYLE_USAGEs; three STYLED_ITEMs all bound to the same ADVANCED_FACE.

Expected kernel behavior

Heal and accept: writers must heal/de-dup COLOUR_RGB by (R, G, B) tuple equality before emission. Receivers should also normalize by pooling on tuple value, not entity identity, to avoid this bug's downstream UI clutter. Warn and accept with W_DUPLICATE_COLOUR when redundant entries are observed; emitting hundreds of copies of the same colour without diagnostic is a coverage gap.

Notes

**See also**: Xp034 (sRGB shift). Synonyms: "duplicate COLOUR_RGB entities", "STEP file bloated by redundant colors", "same-valued colors not pooled", "writer doesn't de-dup colours", "hundreds of identical RGB entries".

Expected validation

occt=empty/empty gmsh=empty ifc=schema_n/a

Byte assertions

  • count(b'COLOUR_RGB') >= 3
