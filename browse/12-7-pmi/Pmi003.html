Pmi003 — Stacked vs composite tolerance frames mis-tagged

§12.7 (sub-class: composite-tolerance)

P1 — silent data loss

round-trip pmi

View raw fixture (.stp) step-examples/12-7-pmi/Pmi003.stp

Sources

  • 02-caxif (PMI v4.1 §10.1.1.2 Fig 108), 11-translator-vendors (W026)

Description

Multiple `geometric_tolerance` rows grouped only for visual presentation ("stacked") are semantically independent. True "composite" tolerances must be linked by a `geometric_tolerance_relationship` whose `name` is `'composite'`. Writers that always emit `geometric_tolerance_relationship` with `name='composite'` (or who flatten composite frames into independent tolerances on export) inflate or destroy composite counts.

Reproducer recipe

Two parallelism tolerances drawn one above the other in the same FCF, written with `geometric_tolerance_relationship('composite', t1, t2)` even though they are merely stacked. Conversely, a true composite position tolerance written as two unrelated `position_tolerance` instances.

Expected kernel behavior

Heal and accept: use the `name='composite'` relationship strictly for true composite tolerances; preserve composite frame structure across round-trip.

Notes

Synonyms: "stacked tolerance frame mistagged as composite", "GD&T frames merged when they should be stacked", "tolerance frame stack/composite distinction lost".

Expected validation

occt=shape(1)/shape(1) gmsh=shape(1) ifc=schema_n/a

Byte assertions

  • count_entity_def(b'PARALLELISM_TOLERANCE') == 2
  • contains(b'GEOMETRIC_TOLERANCE_RELATIONSHIP')
  • contains(b'composite') or contains(b'stacked')

Tier-3 assertions

  • shape_null == False
  • n_vertices_total == 1
