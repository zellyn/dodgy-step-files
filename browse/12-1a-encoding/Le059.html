Le059 — German umlauts in `PRODUCT.name` mis-decoded by reader (Latin-1/UTF-8 confusion)

§12.1a encoding/strings (sub-class: Ed.2 vs Ed.3 default-encoding mismatch on PRODUCT.name)

P1 — silent data loss

encoding

Sources

  • OCCT MANTIS#0032409
  • bug-reporter language: "bug in OCC with german letter", "umlaut in part name appears as garbled bytes", "ä emitted as raw 0xE4 misread as UTF-8". (OCCT MANTIS tracker 502 as of 2026-05-02)

Sender

German-locale CAD authoring tools (Catia / NX / Solid Edge German installs) that emit Ed.2 STEP with raw ISO-8859-1 bytes for `PRODUCT.name` like `'Schrägverzahnt'`.

Description

A producer emits Ed.2-style STEP where `'ä'` appears as raw byte `0xE4` inside the string literal; schema-legal under the Ed.2 default of ISO-8859-1. The current reader assumes Ed.3 UTF-8, sees an isolated continuation byte, and either replaces with `?`, drops the character, or (in older builds) overruns into the next byte and corrupts the string. The producer's intent is preserved on disk; the receiver mangles it on import.

Reproducer recipe

`#100=PRODUCT('Schr\xe4gverzahnt','','',(#101));` — the bytes `0xE4` should decode to `ä` per Ed.2 default; UTF-8-only readers misinterpret.

Expected kernel behavior

heal-and-accept; inspect `FILE_DESCRIPTION`'s `implementation_level` and conformance class to determine edition; on Ed.2, decode high-bit bytes as ISO-8859-1; on Ed.3, decode as UTF-8 and reject isolated continuation bytes with `E_BAD_UTF8`.

Notes

**See also**: Le002, Le021. Synonyms: "bug in OCC with german letter", "umlaut in PRODUCT.name garbled", "ISO-8859-1 ä misread as UTF-8 by STEP reader", "high-bit byte mis-decoded in part name".

Expected validation

occt=shape(1)/shape(1) gmsh=shape(1) ifc=schema_n/a

Byte assertions

  • contains(b'\xe4') or contains(b'\xf6') or contains(b'\xfc')
  • contains(b'PRODUCT')

  • shape_null == False
  • n_vertices_total == 1
