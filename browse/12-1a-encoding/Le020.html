Le020 — String literal exceeds Ed.3 32 769-octet limit

§12.1a encoding/strings (sub-class: limits)

crash spec-violation encoding

View raw fixture (.stp) step-examples/12-1a-encoding/Le020.stp

Sources

  • N013/ISO 10303-21 Ed.3 §6.4.3.5
  • Q074/StepFile/step.lex:64-67 (Henri.stp / 401.stp)

Description

Ed.3 caps a single STRING literal at 32 769 octets, including apostrophes and any encoded escape sequences. Tools embedding base64 thumbnails, long descriptions, or property-set dumps exceed this silently, and naive parsers overflow fixed-size string buffers when the literal length exceeds the spec cap (real-world examples: Henri.stp / 401.stp).

Reproducer recipe

a single attribute STRING of length 50 000 octets.

Expected kernel behavior

spec rejects beyond the limit; tolerant readers may accept and warn but must guard against integer-overflow in length fields.

Notes

**See also**: Ad001, Lh010. Synonyms: "string literal too long", "thumbnail base64 exceeds STEP string limit", "32769-byte cap exceeded", "huge embedded blob overflows string buffer", "long property value crashes parser".

Expected validation

occt=reject/reject gmsh=reject ifc=schema_n/a

Byte assertions

  • max_string_literal_length > 32768
  • length > 32768
  • matches(rb"PERSON\(\s*'p1','A{1000,}")

Tier-3 assertions

  • load != "ok"

Cross-references
