Ad080 — Two `DATA` sections with colliding `#NNN` id space in one file (token-boundary attack)

§12.11 (sub-class: framing / fuzz-class)

adversarial

View raw fixture (.stp) step-examples/12-11-adversarial/Ad080.stp

Sources

  • 12-adversarial.md A025

Description

Two `DATA;…ENDSEC;` sections appear in one file (illegal in Ed.2), often with concatenated section markers. Common attack shape: both DATA sections reuse the identical entity-id range `#1`.`#N` so any reader that builds a single `#`-keyed map silently overwrites the first section's entities with the second. Greedy regex parsers may match across the section boundary.

Reproducer recipe

`…ENDSEC;DATA;…ENDSEC;DATA;…ENDSEC;`

Expected kernel behavior

reject second `DATA` section unless Ed.3 multi-section; one DATA per file otherwise.

Notes

**See also**: Lh024, Ls024. **OCC behavior**: emits a diagnostic but produces no shape (warn-and-proceed by oracle, but result is empty); outside catalog's allowed set ({reject}). Kernel-bug witnessed: receivers must reject this fixture per the catalog's stated invariant.
